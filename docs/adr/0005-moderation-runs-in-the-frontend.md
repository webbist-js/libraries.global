# Moderation runs in the frontend

## Context

Until September 2026 every Submission was reviewed in the Strapi admin's moderation queue, and the access spec (`docs/superpowers/specs/2026-09-26-access-contribution-pro-implementation-design.md` §12) kept a frontend moderator queue out of scope. Reviewing in Strapi admin means every reviewer needs an admin account, and admin roles can't express what moderation now needs. Contributor trust has moved to Role Grants: one person can hold several roles, and a Moderator grant is scoped to a Moderation Queue (`index`, `knowledge`, `journal`, `applications` or all of them) and optionally to one locale. Knowledge and Journal suggestions, Role Applications and Location Requests all need reviewers who aren't the owner, and very few people should have Strapi admin access.

## Decision

Community Moderators review Submissions at `/contribute/moderation`: a queue filtered to their Moderation Scopes, a review page for each Submission, and a decision form with Approve, Approve and publish (for article suggestions, new articles from non-editors and new libraries), Needs changes and Reject. The Moderation tab shows only for sessions with `moderate.queue`. The Next routes under `/api/moderation/*` are fast pre-checks. Strapi re-authorises every moderation request with `canModerate` from `@repo/access`, using the caller's current Role Grants and the bridge identity. An out-of-scope Submission reads as missing, and nobody can open or decide their own Submission. Strapi admin keeps a thin queue for the owner, and both surfaces share the same service methods, transitions and Review Events. No Plan, Entitlement, Tier or role lets a Submission skip review. This supersedes the frontend-queue exclusion in §12 of the access spec. That spec's decision I5, that only the owner has Strapi admin access, still holds, and moderation no longer needs admin access.

## Consequences

Moderators sign in to the site like any contributor, and their scope is a Role Grant the owner can give, narrow or let expire without touching admin roles. Every moderation route has to be authorised twice, once by a Next pre-check and then by Strapi, and Strapi's check is the one that counts. Reviewer ids carry a prefix, `ba:` for community Moderators and `admin:` for the owner, so self-review checks and the Review Event log work across both surfaces. The admin queue must stay in step with the frontend one: a change to transitions, apply logic or scope rules goes in the shared services, not in either UI. The access E2E covers tab visibility, scope filtering, self-review denial, approve-and-publish and the needs-info note (`qa/tests/playwright/e2e/access/moderation.spec.ts`).
