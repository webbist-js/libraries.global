# Implementation spec: Explorer, earned Supporter, verified Staff, API Access and sponsorship

Status: implementation brief for Claude Code, 5 November 2026. This document specifies the intended end state and acceptance evidence. It does not authorise live billing activation, production publication or deployment. The commercial model is described in [the pricing proposal](sponsored-access-pricing.md). Repository `AGENTS.md`, `apps/ui/PRICING.md`, `apps/ui/TEAM-API.md`, `apps/ui/TEAM-BILLING.md`, `apps/strapi/CONTENT-OPERATIONS.md` and the private deployment runbook remain required reading. Keep operational details and customer data out of Git.

## 1. Deliverable and non-negotiable boundaries

Deliver a working, independently billed £100/month API product; free Explorer and verified Staff capabilities; earned Contributor/Supporter recognition; a sponsorship proposition; bounded overages; service, submission and analysis APIs; revised reference/playground; and matching UI, Knowledge and legal drafts. Do not activate new live purchases or publish production legal/Knowledge copy as part of coding. Existing settled subscriptions, accepted consent versions and immutable Stripe Price IDs remain historically correct and manageable through migration. No payment, sponsorship or API key may grant staff verification, record publication or editorial priority. No free browser route may become an unmetered proxy for paid machine access.

Use feature flags for `new_access_model`, `standalone_api_checkout`, `api_overage`, `api_service_reads`, `api_submissions` and `api_analysis`; default off in production until each acceptance gate. A flag must not bypass authorization or accounting. Rollback must turn off new entry points while preserving paid access to any already-sold subscription and the ability to cancel it. Do not remove database columns needed for historical billing in this release.

The `Contributor` threshold is one accepted contribution. The `Supporter` threshold is 100 accepted contributions, counted by accepted submission/suggestion identifiers, not raw point total. Existing earned-Pro point state and 30-day expiry must be migrated into historical recognition, not silently equated to 100 contributions. Existing paid Supporter/Pro/Team subscribers need a separate transition campaign: stop new sales, keep cancellation/invoice access, notify before renewal, and obtain a reviewed refund/credit or contract-migration decision rather than charging for newly free capabilities. Existing agreed invoice Teams are handled individually. Leave the legacy billing worker able to reconcile refunds and disputes until records expire.

Explorer's initial human export ceiling is 10,000 rows per action and 20 exports per rolling day per account; do not advertise bulk dataset delivery. Saved views/searches retain the present Pro ceiling but need abuse monitoring. Contributor Reach uses the existing single-library size/zoom and source-coverage checks; cache hits do not spend the two-job allowance. API account owners/organisers with settled coverage get the existing standard Pro browser Reach limits: 20 new jobs/hour, at most 50 eligible libraries and the existing 2,500 km² / 75 km four-time or 20,000 km² / 200 km selected-time envelope. Add a pooled 100 new browser Reach jobs/day per API customer. No other API customer member inherits this bonus automatically. API job credits are separate. Verified Staff has no special Reach multiplier merely by being staff. Keep native cell, time, queue and memory admission.

## 3. API subscription, limits and billing semantics

One customer owns one pooled allowance across all keys and applications. Snapshot at checkout: 10,000 successful requests, 250 MiB (= 262,144,000 uncompressed JSON bytes), 100 analysis credits, 30 attempted requests/minute, two concurrent requests, 128 KiB response body and at most 50 list records. Keep unlimited key count with existing key-mutation rate control. Existing £15 snapshots retain their 100,000-request/10-GiB purchase terms until explicitly migrated. Each new snapshot includes offer version, price ID, tax behaviour, limits, overage rates and consent version; later environment changes do not alter it.

The billing period is the settled Stripe subscription item period, UTC timestamps `[start,end)`, rather than the current calendar month. Partial first periods get full allowances, as the existing API offer does. Renewal creates a new allowance only when the next paid period is established; a failed payment cannot create free new usage. Cancellation allows settled access through the paid end unless a full refund/dispute hold removes it. A past-due grace period must never authorize unbilled overage. Document the exact paid-through and quota-period behaviour in terms and dashboard. Migrate counters without duplication; preserve old calendar-month usage records for audit.

Overage is disabled until the customer owner/organiser explicitly opts in and accepts new API terms. Rates beyond the included totals: **1 penny per additional successful request; 10 pence per additional MiB of response data; 50 pence per additional completed analysis credit**. Calculate byte overage from total excess bytes with decimal precision, round each _period's invoice line_ to the nearest penny, and do not round each request up to a MiB. Show rates, included units, used units, projected overage and next invoice. The customer chooses a monthly cap from £10 to £500 in £10 steps; preselect £100 in the UI but do not enable it without an affirmative action. Changing the cap is versioned and auditable; reducing it below accrued charges stops further paid usage and does not erase the charge. Turning overage off does the same. Do not bill failed, refused, timed-out or internally retried work. The cap applies to aggregate request, byte and analysis overage before tax; show that basis in UI and terms. An endpoint may be refused early if its worst-case reservation would cross the cap. No negative credit balance or uncapped overdraft is permitted.

Use the application PostgreSQL ledger to atomically reserve capacity before doing work. Reserve one request, maximum allowed response bytes and the operation's analysis credits under one customer/period lock; reconcile actual successful bytes and completed credits; refund unused reservations. A completion and its ledger event must be idempotent. Recover abandoned reservations with the existing maintenance worker. For response overflow, fail closed without delivering an unmetered payload. For async jobs reserve credits at acceptance, settle once on completed result, refund failure/expiry, and retain a stable job ID across retries. A result fetch consumes request and response bytes, never a second analysis credit. Cached identical work also consumes delivery units only. The authoritative cap check includes concurrent reservations. Expose remaining units and reset time through response headers and dashboard. Return 429 with a stable code (`quota_requests`, `quota_bytes`, `quota_analysis`, `overage_cap`, `rate_limit`, `concurrency_limit`) and `Retry-After` where meaningful.

Stripe: create a new immutable £100 monthly recurring Price and separately metered overage Prices/meter configuration in sandbox first. Reuse the repository's supported Stripe client/API version; check current Stripe meter constraints before implementing. Use one durable ledger event ID as the Stripe idempotency identifier. Deliver usage asynchronously with bounded retries, dead-letter state and reconciliation by customer/period/dimension. The app, not Stripe, decides admission in real time. Do not mark a period reconciled until Stripe's invoiced quantities and amounts match the local ledger and payment state. Webhook handling must be signed, replay-safe, order-independent and mode-bound. Subscription status or checkout return alone never grants access; settled invoice lines and the correct Price/customer binding do. Test threshold warnings at 50/80/100%, meter lag, failed delivery, invoice mismatch, payment failure, refund and dispute holds. Keep sandbox and live IDs separate. No automatic live catalogue creation or checkout enabling from a build.

## 4. Account and authorization model

Replace rank-based `public/free/supporter/pro/team` access resolution with independent facts: signed-in Explorer, accepted-contribution recognition, verified scoped staff grants, active paid API account and grandfathered paid obligations. Keep a compatibility projection for old session consumers during migration; remove legacy plan checks only after call sites and tests are converted. A `team`/organisation may remain an administrative container, but active paid seats no longer define staff access or API eligibility. Verify every staff mutation against current claim/authority grant and library scope at request time. A Team organiser may manage organisation and API billing without being permitted to edit every covered library. Sponsorship is data in a separate administrative record, never an entitlement source.

An API customer can be individual or organisation. Define account owner, billing manager and key manager roles, a transfer path, and exactly one active billing subscription per API account. Existing Team API customers map to the same API account model without changing customer, subscription or keys. A person can administer an API account and separately belong to a Staff workspace. Key auth is independent of browser sessions; API scopes are independently revocable and never convey a signed-in user identity. Account deletion needs billing cancellation/retention handling and an owner-transfer block where others rely on the account.

## 5. Machine API contract

Keep existing `search:read` and `libraries:read` routes. Add `services:read`, `analysis:run` and `submissions:write`. New keys default to read scopes only; write and analysis scopes require explicit confirmation. Keys retain SHA-256 digest-only storage, one-time reveal, revocation and regeneration. All `/api/v1` requests must pass the same key authentication, customer coverage check, scope check, limiter, ledger and bounded private CMS bridge. The playground must use these production routes with an entered key kept in page memory and count its usage.

| Endpoint                                | Input/output contract                                                                                                   | Additional validation                                                                                                    |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `GET /api/v1/services`                  | Published services/networks, locale, filters, opaque cursor, max 50.                                                    | Explicit projection; source attribution; no private memberships.                                                         |
| `GET /api/v1/services/{ref}`            | One published service with stable public ref and coverage metadata.                                                     | 404 for unknown/private ref; canonical ref validation.                                                                   |
| `GET /api/v1/services/{ref}/libraries`  | Published member libraries, opaque cursor, max 50.                                                                      | Membership from CMS, not caller-supplied IDs.                                                                            |
| `POST /api/v1/submissions/libraries`    | New-library proposal, evidence/source, client idempotency key; returns proposal ID/status.                              | Strict body cap, schema, duplication detection and moderation queue. Never publish directly.                             |
| `POST /api/v1/submissions/corrections`  | Published entity ref, field-scoped proposed corrections and evidence; returns proposal ID/status.                       | Reject protected fields and arbitrary CMS paths; handle merge/conflict review.                                           |
| `GET /api/v1/submissions/{id}`          | Status and safe result for the submitting API account.                                                                  | Ownership check; no reviewer notes/private identities.                                                                   |
| `POST /api/v1/analysis/summary`         | Bounded published service/area analysis; returns completed result or `202` job ID.                                      | 1 credit for simple summary, 5 for richer joins; define operation variants in OpenAPI.                                   |
| `POST /api/v1/analysis/reach`           | `mode` (`library` or `service`), published ref, travel mode and allowed minutes; returns `202` job ID or cached result. | 5 library credits, 20 service credits. Network mode (40 credits) remains behind a separate capacity flag and acceptance. |
| `GET /api/v1/analysis/jobs/{id}`        | Job state, expiry, metering status and safe error.                                                                      | Customer ownership, bounded polling/rate.                                                                                |
| `GET /api/v1/analysis/jobs/{id}/result` | Completed result, below 128 KiB; large geometry unavailable in base API.                                                | Customer ownership, published-field projection, attribution, standard response-byte meter.                               |

For `/services`, choose the canonical CMS Network/service identifier and add a stable public ref if existing slugs can change. Do not claim all networks are public-library services. Specify service type and membership semantics in the response. Reuse current API locale rules: accept a locale only when content is live; do not treat supported UI locales as proof that content exists. Search/list/detail retain existing cursor and attribution contracts. Explicitly version response schemas and error codes in `public/openapi.json` and the human reference.

Submission keys create **untrusted proposals** by default. They cannot assert staff identity, bypass review or receive contribution rewards. If a future delegated staff submission flow is required, use a separate short-lived user authorization tied to a verified scope and auditable consent; do not infer it from the paid key. Connect to the Content Moderation plugin through a dedicated private route that whitelists fields and records submitter account, source licence, idempotency key and review history. Rewards are credited only after acceptance to an attributable human account, once per accepted proposal. Rate-limit writes per key/customer and detect duplicate payloads. Return generic errors where revealing a record's private status would leak information.

Analysis jobs must use existing CMS/native admission, canonical service membership and country dataset coverage. Revalidate current paid status and key scope before result delivery. Put a queue ceiling per customer and globally; cancellation, timeout and worker restart must resolve reserved credits exactly once. Do not accept arbitrary polygons, coordinate arrays, client-selected library memberships, upstream URLs or unbounded batch requests. Avoid storing private query text in usage logs. Define job-result expiry and deletion; mask personal fields and keep source licence/attribution. Asynchronous API requests must not call the browser's session-only Atlas routes as an authorization shortcut.

## 8. Implementation sequence and evidence for review

1. **Inventory and design checkpoint:** dependency graph of entitlement checks, all pricing/content references, current Stripe/API schema, live Knowledge locale inventory (read-only), cost measurements for request bytes and Reach jobs, migration design, and OpenAPI draft. Record decisions that differ from this spec before coding.
2. **Independent access migration:** new capability facts, Contributor/Supporter recognition, free Staff path, restrictive Reach enforcement, compatibility projection, legacy subscription handling. Prove no paid/sponsor status grants staff editing and no existing editing permission is lost accidentally.
3. **Standalone API account and billing:** new customer binding, £100 sandbox catalogue, consent, period snapshots, quotas, opt-in overage ledger, Stripe meter delivery/reconciliation, dashboards and portal. Prove settlement, cancellations, spend cap, race handling and recovery with one test worker and local existing database only.
4. **API slices:** service reads; moderated submissions; bounded summary analysis; asynchronous Reach. For every slice update routes, CMS plugin bridge, OpenAPI, reference, playground, docs and negative authorization/accounting tests together. Generate Strapi types after any schema change.
5. **UI/content migration:** customer-facing names, Staff/Developer workflows, sponsor proposition, localised messages, staging-ready Knowledge and legal drafts, removal of obsolete purchase entry points, regression checks.
6. **Handoff to Codex:** provide a concise implementation report with changed files, migration commands, new flags and IDs as placeholders, irreversible operations, test results, known limitations, required legal/content review and rollback instructions. No private credentials or infrastructure details in public artifacts.

Run finite checks sequentially with capped Node memory and one test worker, per repository instructions. At minimum: package typechecks/lint, access and billing tests, transactional quota/concurrency tests, API gateway/route tests, CMS plugin tests, native analysis tests, OpenAPI/reference consistency, locale/content-script tests, and targeted browser acceptance against the existing single local Next/Strapi stack. Include malformed/oversized requests, cross-account access, scope denial, expired/revoked keys, duplicate webhook/meter/job events, quota boundary races, refund/dispute, moderation replay, staff privilege escalation and queue exhaustion. A source test is not evidence of a settled Stripe payment. Codex will independently review the diff and evidence, run appropriate acceptance checks, and coordinate any production promotion under the private release runbook. Production Stripe/catalogue writes, legal publication, Knowledge publication and deployment remain separate gated actions.
