# Proposal: free participation, verified staff, paid API and sponsorship

Status: decision proposal, 5 November 2026. No prices, permissions, purchases or production content change by publishing this document. Amounts and allowances below are proposed launch values in GBP, subject to cost measurement, customer interviews, tax review and owned sandbox acceptance.

## Product promise and names

| Name           | Eligibility                                                                  | What it gives                                                                                                                                                                                                         | Charge               |
| -------------- | ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| Explorer       | Any account                                                                  | Discovery, saved tools, comparison, context layers, alerts and modest human-scale export. Existing Pro UI capabilities become standard, subject to fair-use limits.                                                   | Free                 |
| Contributor    | Accepted contribution; Supporter recognition earned at a published milestone | Recognition, contribution history and a small, explicit Reach allowance. Supporter is an earned badge/status, not a purchase or an editing role.                                                                      | Free                 |
| Verified Staff | Verified affiliation and scoped library authority                            | Staff workspace, approved library editing, collaboration, embeds and appropriate organisation controls. Authority remains scoped to libraries or services; joining an organisation alone grants no editing authority. | Free                 |
| API Access     | Organisation or individual with a paid API subscription                      | Production machine access, keys, usage dashboard, reference and playground. No paid Team seat prerequisite.                                                                                                           | £100/month, proposed |
| Sponsor        | Organisation funding the public service                                      | Acknowledgement and an impact report; optional separate API contract. No influence over records, ranking, verification or editorial review.                                                                           | Annual agreement     |

Retire the customer-facing Pro and Team plan labels. “Staff workspace” can retain an organisation container, members and an organiser, but its paid seat state must cease to control verified staff tools. Do not infer verified status from payment, sponsorship, an API key or a Contributor badge. Replace the existing 5,000-point/30-day earned-Pro hold with a separately defined, durable Supporter recognition milestone. Approved contribution types and anti-abuse rules remain in the rewards system. Start with one accepted, substantive, moderated contribution for Contributor status; set a higher published milestone for Supporter recognition after inspecting actual reward distribution. Never award editing rights for points.

Explorer gets the former Pro browse, comparison, saved-view, alert and export features, with reasonable per-action and account limits. Reach is the expensive exception: no service or network Reach calculation for an ordinary Explorer account; a Contributor receives **two new one-library Reach calculations per rolling seven days**, no bulk/network Reach, and cached repeats of the same result are free. This replaces the current earned-Pro allowance of 20 new analyses/hour and its large geographic envelope. An account that administers an active API subscription receives the former standard Pro interactive Reach allowance (20 new calculations/hour, up to 50 eligible libraries and the existing geographic envelopes) as a bonus, with an additional organisation-wide daily compute ceiling. This bonus is independent of staff verification and ends when settled API coverage ends. Do not extend it automatically to every member of a customer organisation. The paid machine API has its own analysis quota below, so browser work cannot evade API metering or vice versa. Keep the native service's area, cell, timeout and queue admission checks.

## API launch offer and overages

Proposed base: **£100/month** for one customer account, including **10,000 successful API requests, 250 MiB of uncompressed JSON response data and 100 analysis credits per billing period**. This reduces the current 100,000 requests and 10 GiB considerably. Set 30 attempts/minute, two concurrent requests, 128 KiB maximum JSON response and 50 records per page. Count every successful response against requests and bytes; failed requests still count for abuse/rate control. Cache hits count. Analysis credits are charged only for completed new jobs: one-library Reach 5, service Reach 20, network Reach 40, lighter non-Reach analysis 1–5 according to a published endpoint table. A cached identical result does not charge another analysis credit, but delivery still consumes request and byte allowance. Reject jobs that cannot fit the remaining analysis allowance before starting them. Large exports and media delivery need their own explicit contract rather than bypassing the response cap.

Overage is **off by default**. When the customer opts in, proposed prices are £10 per additional 1,000 requests, £10 per additional 100 MiB and £50 per additional 100 analysis credits, calculated on actual units above the included amounts (prorated to the unit, not rounded up to a whole block). Show the exact live accrued charge and an estimated next invoice. Require a customer-set monthly overage ceiling; default the selectable ceiling to £100, with a self-service maximum of £500. Stop new requests or jobs at the first exhausted allowance when overage is off or its ceiling would be exceeded; return a documented 429 with remaining balances. Never permit unbounded usage because a Stripe meter or webhook is delayed. Send warnings at 50%, 80% and 100% of each allowance and of the spend ceiling. No automatic charge for refused or failed work.

Use the application ledger as the immediate admission authority and Stripe as the invoice authority. Persist a uniquely identified, immutable usage event for each settled request and completed job; meter delivery needs idempotent retry, reconciliation and a dead-letter path. Verify that the invoiced total equals the application ledger before treating a cycle as reconciled. Align allowance and spend-ceiling reset with the paid subscription billing period; migrate the current calendar-month counter carefully, preserving purchased snapshots and avoiding a double allowance at transition. Stripe supports metered prices and usage alerts, but its reporting is not the real-time hard stop; enforce that locally. [Stripe invoice price model](https://docs.stripe.com/api/invoices/object), [billing alerts](https://docs.stripe.com/api/billing/alert/deactivate).

VAT treatment and whether the £100 is tax-inclusive or exclusive must be fixed in the offer and displayed consistently at checkout, invoice and legal copy. Keep existing subscriber prices and accepted terms until an explicit migration or agreed cancellation. Do not silently replace £15 Team API subscriptions with £100 subscriptions.

## New paid API contract

Keep existing versioned search, library record and place read routes. Add the following in separately accepted slices, each reflected in OpenAPI, reference pages, playground examples, key-scope controls and usage accounting:

| Resource         | Proposed route family                                                                           | Boundary                                                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Services         | `GET /api/v1/services`, `GET /api/v1/services/{ref}/libraries`, `GET /api/v1/services/{ref}`    | Published service/network identity, stable pagination, licensed field projection and source credit; service membership is not staff authority.                                                                                                       |
| Analysis         | `POST /api/v1/analysis/summary` and job status/result routes                                    | Published, bounded inputs; asynchronous jobs for costly calculations; per-key and customer quotas.                                                                                                                                                   |
| Reach            | `POST /api/v1/analysis/reach` and job status/result routes                                      | One-library and service modes first; network mode only after capacity and consent review. Validate coordinates, geography, service membership and source coverage in CMS and native service. No arbitrary national polygon or oversized bulk result. |
| Data submissions | `POST /api/v1/submissions/libraries`, `POST /api/v1/submissions/corrections`, and status lookup | Authenticated proposals enter the existing moderation workflow. They never publish directly or grant points until accepted. Duplicate detection, evidence/source requirements and reviewer audit apply.                                              |

Use separate `services:read`, `analysis:run` and `submissions:write` scopes; default new keys to read only. A paid key authenticates the client, not the identity or authority of a library staff member. Any submission claiming to act for a specific library requires an additional delegated user/organisation authority flow, or must be presented explicitly as an untrusted public suggestion. Never let a machine key call staff/admin CMS mutations. Reuse existing moderation policies for review, abuse controls, idempotency and accepted-contribution credit. Avoid storing private source material or personal data in usage logs. Define retention for submitted payloads and job results in the privacy notice.

The API gateway must check paid coverage, key scope, request shape, per-minute/concurrency budgets, request/byte/analysis quota and spend ceiling before dispatch. Reserve the maximum potential cost transactionally, settle actual usage after successful response, and release failed reservations. Existing Stripe invoice settlement remains required to open paid access. For async analysis, reserve at job acceptance, settle on completion, refund on failure or timeout, and prevent retry/replay from starting two charged jobs. Apply the same rules in the playground; do not make a private unmetered execution path. New routes must use explicit published-field projections, locale/attribution metadata, bounded pagination and the current private CMS bridge rather than exposing Strapi or the analysis service directly. Add negative tests for cross-customer keys, revoked/lapsed coverage, wrong scopes, excessive bodies, race conditions at quota edges, spend ceilings, replayed submissions and failed jobs.

## Sponsorship proposition

Offer three annual conversation anchors: **Community Sponsor £2,500**, **Service Sponsor £5,000**, **Founding Sponsor £10,000**. These are suggested asks, not automatic entitlements. Sell a concrete programme: public access, data quality work, translation, geographic coverage or open tooling, with quarterly activity and annual impact reporting. A sponsor receives an optional name/logo acknowledgement, a factual sponsor page entry and briefings. Neither priority in search nor privileged editorial treatment is included. Sponsorship must not be described as a charitable donation or tax-deductible unless the organisation's legal status supports that claim. A sponsor that needs API access signs up under the API offer or a separately priced, explicit bundle; the sponsorship amount does not silently purchase metered capacity. Track sponsor agreement, term, recognition consent, attribution assets and reporting obligations separately from API usage and staff authority.

## Changes to the current implementation

1. **Access model:** revise `packages/access/src/entitlements.ts`, earned-Pro/reward code, session claims and access-plugin plan/Team services. Replace plan inheritance with independent capability dimensions: Explorer, earned recognition, verified staff authority, API subscription and any grandfathered paid grant. Drop paid seat dependence from staff workspace, widgets, invitations and library-scoped capabilities; preserve ownership/handover and scoped editing checks. Add distinct browser Reach and machine analysis budgets. Migrate historical access without granting everyone staff authority.
2. **Billing and tracking:** update `apps/ui/src/lib/membership-pricing.json`, personal billing and Team billing flows, checkout/portal/catalogue scripts, webhook worker, Team API projection, database schema and API accounting. Add standalone API customer ownership, period-based quotas, analysis credits, opt-in overage/cap records, usage events, meter delivery/reconciliation, invoice display and failure recovery. Make cancellation, refunds, chargebacks and account deletion cover the new billing object. Archive old products/prices only after existing subscriptions are dealt with; immutable historical Price IDs and accepted offer snapshots remain valid.
3. **API and CMS plugins:** extend `apps/ui/src/lib/team-api`, `/api/v1` routes, `public/openapi.json`, request reference and playground. Extend the Strapi Access plugin bridge, scoped record projections and service membership reads; connect the Content Moderation plugin for submissions, the Rewards plugin for accepted contributions and the Events plugin only where event resources are later promised. Recheck the Beta Invites gate and the API bypass, CMS permissions, service tokens, rate limits, audit trails and Meilisearch queries. Native `apps/analysis` remains behind the private bridge. Generate Strapi types after any schema change.
4. **Pages and navigation:** replace `/membership` and `/contribute/membership` plan cards, comparison, FAQ, roadmap, checkout and status copy with Explorer, Contributor, Verified Staff, API Access and Sponsor. Update profile membership/billing to separate earned status, verified authority and API billing. Convert `/staff/teams/new`, `/staff/teams/billing`, staff team pages, invites, widgets and organiser copy to free verified staff organisation management. Make `/developers` the standalone API purchase, key, usage, overage, invoice, reference and playground home. Add a sponsor information/contact page and acknowledgement surface. Update homepage, footer, navigation, Atlas upsells, empty states, transactional emails and translated UI messages. Remove unused personal paid checkout, Pro upgrade and seat purchase controls after migration, keeping legacy billing management reachable for existing customers.
5. **Knowledge and legal:** inventory the live Knowledge catalogue by document ID and locale before edits. At minimum revise plans/pricing, membership/billing, earned access and rewards, verified staff/Team guides, API overview/onboarding/reference/playground, Atlas/Reach/export, data reuse/licensing, submissions/moderation, cancellation/refunds, account deletion and sponsorship information. Update every published locale of each affected article. Current scripted rollouts cover English, French and Czech; supported UI locales also include Spanish, so check whether Spanish Knowledge variants exist and create or correct them where the article is offered there. Preserve links, media, SEO, authorship and unrelated edits; stage copy until matching routes and pricing are accepted. Audit `apps/strapi/scripts/{billing,team-api-knowledge,atlas-knowledge,rewards-guide,homepage-refresh}-content.mjs` and their update helpers so a later run cannot reintroduce old copy.
6. **Production legal pages:** prepare reviewed new revisions of general terms, membership/API terms, cancellation and refunds, privacy and data reuse/licensing. Explain £100 recurring charge, tax, included allowances, metering, opt-in overage prices/cap, billing period, suspension and disputes; distinguish sponsorship from purchase; explain submission ownership, moderation, retained payloads, attribution, analysis limitations and rate controls. Review cookie copy if tracking changes. Publish only after legal review and matching production release acceptance, preserving historical terms and consent evidence.

## Release sequence and decision gates

First measure current API/Reach cost and interview likely buyers and sponsors; validate the £100 offer and the 250 MiB limit against real integration patterns. Then implement independent entitlements and standalone billing with migration/legacy support. Launch read-only API at the new price with bounded overage and reconciliation. Add service reads, submissions and async analysis/Reach as separately tested releases. Complete sandbox purchase, overage invoice, refusal-at-cap, refund, cancellation, job-failure and abuse acceptance before live activation. Stage all affected Knowledge translations and legal revisions, then publish with the corresponding production release. Remove old UI and catalogue entry points only when no customer needs them to manage an existing agreement.
